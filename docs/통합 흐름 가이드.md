# 통합 흐름 가이드

현재 구현을 실행 시작부터 종료까지 따라가는 문서입니다. 사용자가 정한 기본 구조와 구현 과정에서 추가한 보조 요소를 함께 설명합니다. 코드 참조는 **2026-10-19 현재 파일과 줄 번호**입니다. 이후 코드가 바뀌면 줄 번호도 달라질 수 있으므로 함께 적힌 함수 이름을 함께 확인하세요.

**읽는 방법:** 클릭 링크 없이 파일명·줄 번호·함수 이름을 일반 텍스트로 표시했습니다. 아래 예시로 흐름을 확인하세요. 예시는 이해를 위해 축약한 것이며 그대로 복사해 실행하는 완성 코드가 아닙니다.

기준: Plzz 구현 가이드북. 함수별 세부 설명은 06_CODE_FLOW.md, 실행 명령은 README를 참고하세요.

## 1. 전체 연결

```text
사용자 명령
  → __main__.py
  → cli.main: 명령 해석·저장소 초기화·서비스 생성
  → cli.handle_*: 입력 받기·서비스 호출·결과 표시
  → services.BudgetService: 검증·업무 순서·검색·집계
  → repositories.CsvRepository: CSV 읽기·변환·ID 확보·쓰기
  → data/*.csv
  → 결과가 CLI로 반환
  → 정수 종료 코드가 운영체제로 전달

validators: 서비스와 저장소에서 공통 값 검증
models: Transaction·Category·Budget 자료 전달
errors: 오류 정보를 예외로 전달
decorators.handle_errors: CLI 경계에서 오류를 안내·종료 코드로 변환
```

모든 작업이 위 순서를 끝까지 지나는 것은 아닙니다. 조회는 읽기만 하고, 검증·취소·변경 없음에서는 저장까지 가지 않습니다. 모델은 실행 단계라기보다 모듈 사이에서 전달하는 자료의 형태입니다.

|---|---|
| 실행 진입과 종료 코드 | `budget_app/__main__.py:3` — __main__.py:3 |
| 명령 해석과 서비스 연결 | `budget_app/cli.py:210` — cli.py:210 — main |
| 업무 처리 | `budget_app/services.py:18` — services.py:18 — BudgetService |

| 공통 검증 | `budget_app/validators.py:9` — validators.py:9부터 |

예시: `python -m budget_app --data-dir ./data list`.

3. `budget_app/repositories.py:20` — CsvRepository.__init__:20이 저장 폴더와 네 CSV 경로를 객체에 보관합니다. 생성자 자체는 파일을 만들지 않습니다.

`--help`는 2단계에서 끝나므로 저장 폴더를 생성하지 않습니다. 네 파일의 최초 생성 전체가 한 번에 원자적으로 수행되는 것은 아닙니다.

## 4. 목록·검색: 파일 → 객체 → 필터 → 출력

목록은 `budget_app/cli.py:93` — handle_list:93 → `budget_app/services.py:35` — list_transactions:35, 검색은 `budget_app/cli.py:99` — handle_search:99 → `budget_app/services.py:43` — search_transactions:43으로 연결됩니다.

두 흐름은 아래 읽기 경로를 공유합니다.

1. `budget_app/repositories.py:45` — records:45가 CSV 헤더와 열 개수를 검사하고 문자열 행을 하나씩 내줍니다.
2. `budget_app/repositories.py:118` — iter_transactions:118가 ID 숫자 내림차순·카테고리 참조·날짜·금액·태그를 검사해 Transaction으로 바꿉니다.
3. 목록은 limit만큼 반환합니다. 검색은 기간·분류·유형·메모·태그 조건을 모두 만족하는 거래만 반환합니다.

`yield`를 쓰므로 서비스 함수를 호출하는 순간 전체 파일을 읽지 않습니다. CLI의 for문이 다음 거래를 요청할 때 읽습니다. 이 때문에 오류 처리도 **제너레이터 생성뿐 아니라 실제 순회 구간**을 감싸야 합니다.

손상 행 발견 전 일부 거래를 출력했다면 불완전한 목록이라고 안내합니다. limit로 일찍 끝났다면 읽지 않은 나머지 행까지 검사한 것은 아닙니다.

## 7. CSV 가져오기·내보내기

### 가져오기

`budget_app/cli.py:197` — handle_import:197 → `budget_app/services.py:141` — import_transactions:141.

1. 등록 카테고리가 있는지 확인합니다.
2. `records(..., external=True)`로 외부 CSV를 읽고 `prepare_transaction`으로 각 거래를 검증합니다.
3. 검증한 거래를 임시 JSON 스풀에 쓰고 시작 위치를 8바이트 인덱스 임시 파일에 기록합니다.
4. 입력 전체가 정상이면 `reserve_ids(count)`로 기존 저장 자료도 검사하고 ID 구간을 확보합니다.
5. 내부 함수 `new_transactions`가 인덱스를 뒤에서부터 읽습니다. 입력 첫 행부터 작은 ID를 부여하므로 저장은 입력 역순이어야 ID 내림차순이 됩니다.
6. `prepend_transactions`가 새 거래 스트림 뒤에 기존 거래를 연결하고 `write`가 한 번에 거래 CSV를 교체합니다.
7. CLI가 처리 건수를 표시합니다.

스풀은 임시 보관 파일입니다. JSON은 이 보조 파일에서만 사용하며 영구 저장은 CSV입니다. CSV 물리적 줄을 뒤집지 않기 때문에 여러 줄 메모를 보존합니다. 전체 거래를 list로 모으지 않습니다.

입력 오류면 거래 파일을 바꾸지 않습니다. ID 확보 이후 저장이 실패하면 번호는 공백으로 남을 수 있습니다. 동일 CSV를 재가져오면 새 ID로 중복 등록합니다.

### 내보내기

`budget_app/cli.py:203` — handle_export:203 → `budget_app/services.py:168` — export_transactions:168.

월 하나 또는 시작·종료일 쌍을 검사하고 내부 저장 경로 덮어쓰기를 차단합니다. `search_transactions`로 필터링한 거래에서 id를 빼고 외부 CSV 행을 만듭니다. `write`가 출력 경로 옆의 임시 파일을 완성한 뒤 교체합니다. 실패하면 기존 출력 파일을 보존합니다.

## 8. 모든 저장이 모이는 지점

핵심 공통 함수는 `budget_app/repositories.py:62` — CsvRepository.write:62입니다.

```text
저장할 행 iterable
  → 같은 폴더에 임시 파일 생성
  → CSV 헤더·행 쓰기
  → flush·fsync
  → 파일 닫기
  → os.replace로 대상 파일 교체
  → finally에서 남은 임시 파일 정리
```

행을 만드는 도중 검증 오류가 나면 교체 단계에 도달하지 않으므로 기존 파일이 보존됩니다. 이 보장은 파일 하나의 교체에 해당합니다. metadata와 거래 CSV 전체를 동시에 바꾸는 트랜잭션은 아니며 동시 프로세스 쓰기도 지원하지 않습니다.

## 9. 오류가 발생했을 때의 역방향 흐름

예: CSV 거래 금액이 잘못된 경우.

```text
validate_amount에서 AppError 발생
  → iter_transactions가 파일·레코드 위치를 붙여 data_error로 변환
  → 서비스 순회 중단
  → CLI 순회 중단, 필요하면 불완전 목록 안내
  → handle_errors가 stderr에 원인·힌트 출력
  → 종료 코드 5 반환
  → main → SystemExit(5)
```

`budget_app/errors.py:3` — AppError:3은 메시지·힌트·종료 코드를 담는 예외입니다. `budget_app/errors.py:10` — data_error:10는 저장/가져오기 CSV 오류를 코드 5로 만듭니다. `budget_app/decorators.py:8` — handle_errors:8는 예외를 잡는 실제 실행 경계입니다. errors.py 자체가 오류를 잡거나 화면을 출력하지는 않습니다.

| 코드 | 의미 |
|---:|---|
| 0 | 정상·취소·변경 없음·결과 없음 |
| 1 | 예상하지 못한 내부 오류 |
| 2 | CLI·직접 입력 값 오류 |
| 3 | 없는 대상·중복·미등록·사용 중 등 정책 충돌 |
| 4 | 파일 접근·저장 오류 |
| 5 | 저장·가져오기 CSV 형식/내용 오류 |

handler에서 처리한 오류는 정수 코드로 돌아오므로 main의 데코레이터가 다시 오류를 출력하지 않습니다. main의 경계는 파싱·초기화 오류도 처리합니다. 내부 예외는 화면에 스택트레이스를 표시하지 않으며 DEBUG 로거로 진단 정보를 전달합니다.

## 10. 기본 흐름에 추가한 보조 요소와 이유

아래 요소는 사용자가 정한 핵심 클래스·메서드를 연결하거나 저장 안전성을 지키기 위해 추가했습니다. 정한 이름만 사용한 구현은 아닙니다.

| 추가 요소 | 코드 위치 | 추가한 이유 |

## 11. 코드를 읽을 때 추천 순서

먼저 `__main__ → cli.main → handle_add → 서비스 add_transaction → prepare_transaction → reserve_ids → 저장소 add_transaction → write`를 따라가세요. 그다음 목록의 반대 방향인 `records → iter_transactions → list_transactions → show_transactions`를 읽으면 입력·저장·조회가 연결됩니다. 마지막으로 수정·삭제, 가져오기, 오류 흐름을 읽으면 보조 함수가 필요한 이유를 확인할 수 있습니다.

`self`는 현재 객체, 반환값은 호출한 곳에 돌려주는 값, 타입 힌트는 기대하는 자료형을 적은 계약입니다. dataclass와 타입 힌트만으로 입력이 검증되지는 않습니다. 실제 검사는 validators와 저장소 읽기 경계에서 수행합니다.






## 12. 문서 안에서 보는 코드 예시

아래 코드는 현재 구현의 핵심 연결을 축약한 예시입니다. 생략한 검증·파일 정리·오류 처리는 실제 소스에 있습니다. 각 블록의 주석에 파일과 함수 이름을 표시했습니다.

### 예시 1: 명령 하나가 실행되는 과정

```python
# budget_app/__main__.py
from .cli import main
raise SystemExit(main())

# budget_app/cli.py — main
args = create_parser().parse_args(argv)
repository = CsvRepository(args.data_dir)
repository.initialize_files()
service = BudgetService(repository)
return args.handler(args, service)
```

사용자가 `list`를 입력했다면 args.handler에는 handle_list가 들어갑니다. 저장소 객체 하나를 서비스에 전달해 같은 저장 경로를 사용합니다.

### 예시 2: 입력을 거래 객체로 바꾸기

```python
# budget_app/services.py — prepare_transaction의 핵심
return Transaction(
    id,
    validate_transaction_type(type),
    validate_date(date),
    validate_amount(amount),
    validate_category(category, self.repository.load_categories()),
    memo,
    normalize_tags(tags),
)
```

예를 들어 날짜 문자열 `"2026-10-19"`는 date 객체로, 금액 `"9000"`은 정수 9000으로 바뀝니다. 태그 `"친구, 친구, 점심"`은 `["친구", "점심"]`으로 바뀝니다. 미등록 카테고리나 잘못된 날짜라면 저장 전에 오류가 납니다.

### 예시 3: 검증한 거래에 ID를 붙이고 저장하기

```python
# budget_app/services.py — add_transaction
transaction = self.prepare_transaction(**values)
number = self.repository.reserve_ids(1)
transaction.id = f"TX-{number:06d}"
self.repository.add_transaction(transaction)
return transaction
```

마지막 발급 번호가 7이면 8을 먼저 metadata에 저장하고 TX-000008을 부여합니다. 이후 거래 저장이 실패해도 확보한 번호는 재사용하지 않습니다.

### 예시 4: 파일에서 한 건씩 읽어 화면에 보여 주기

```python
# budget_app/repositories.py — iter_transactions의 흐름을 축약
for row in self.records(self.transactions, TX_FIELDS):
    # 실제 코드는 ID 순서·카테고리·태그도 검사합니다.
    yield Transaction(
        row["id"],
        validate_transaction_type(row["type"]),
        validate_date(row["date"]),
        validate_amount(row["amount"]),
        row["category"],
        row["memo"],
        normalize_tags(row["tags"]),
    )

# budget_app/cli.py — 목록 출력의 핵심
for transaction in service.list_transactions(limit=20):
    show_transaction(transaction)
```

CLI가 다음 거래를 요청할 때 저장소가 다음 CSV 행을 읽습니다. 전체 거래를 리스트로 모으지 않습니다. 검색도 같은 읽기 경로에 조건 필터를 붙입니다.

### 예시 5: 수정 내용을 보여 준 뒤 승인받기

```python
# budget_app/cli.py — handle_update의 흐름을 축약
old = service.get_transaction(args.id)
# 실제 코드는 input으로 changes를 채웁니다.
new = service.preview_update(args.id, **changes)

if new == old:
    print("변경 없음")
    return 0

show_transaction(old)
show_transaction(new)
if not confirm():
    print("취소")
    return 0

service.update_transaction(args.id, **changes)
```

preview_update는 검증한 수정 결과만 만들고 저장하지 않습니다. 확인한 뒤 update_transaction을 호출해야 거래 파일이 바뀝니다. 삭제도 확인 후 delete_transaction을 호출합니다.

### 예시 6: 월별 집계를 끝낸 뒤 출력하기

```python
# budget_app/services.py — get_monthly_summary의 집계 핵심
income = expense = 0
for transaction in self.search_transactions(month=month):
    if transaction.type == "income":
        income += transaction.amount
    else:
        expense += transaction.amount

# 실제 구현은 건수·분류별 TOP·예산도 반환합니다.
result = {"income": income, "expense": expense, "balance": income - expense}

# budget_app/cli.py — handle_summary에서 결과를 받은 뒤 출력
result = service.get_monthly_summary(args.month, args.top)
print(result["income"], result["expense"], result["balance"])
```

서비스가 전체 순회를 끝내야 결과를 반환하므로 도중에 손상 데이터를 만나면 불완전한 합계가 화면에 나오지 않습니다.

### 예시 7: 가져오기와 내보내기의 차이

```text
가져오기:
외부 CSV 한 행 → 검증 → 임시 스풀에 보관
모든 행 정상 → ID 구간 확보
임시 스풀 역순 읽기 → 새 거래 + 기존 거래 → 거래 CSV 교체

내보내기:
월/기간 검사 → 저장 파일 경로 보호 검사
조건에 맞는 거래 한 건 → ID를 뺀 외부 CSV 행
모든 행 정상 → 임시 출력 CSV를 최종 출력 파일로 교체
```

가져오기는 새 ID를 부여하고 내부 저장 파일을 바꿉니다. 내보내기는 기존 거래를 읽어서 별도 CSV를 만듭니다. 두 흐름 모두 최종 파일 교체 전에 오류가 나면 기존 대상 파일을 보존합니다.

### 예시 8: 실제 파일 교체가 일어나는 지점

```python
# budget_app/repositories.py — write의 핵심을 축약
with NamedTemporaryFile(
    mode="w", encoding="utf-8", newline="",
    dir=path.parent, delete=False,
) as stream:
    temporary = Path(stream.name)
    writer = csv.DictWriter(stream, fieldnames=fields)
    writer.writeheader()
    writer.writerows(rows)
    stream.flush()
    os.fsync(stream.fileno())

os.replace(temporary, path)
# 실제 구현은 finally에서 남은 임시 파일도 정리합니다.
```

원본에 직접 한 줄씩 덧쓰는 대신 임시 파일을 완성한 후 교체합니다. 단, metadata와 거래 CSV 두 파일을 동시에 교체하는 것은 아닙니다.

### 예시 9: 오류 정보와 오류 처리의 차이

```python
# budget_app/errors.py — 오류 정보를 만드는 쪽
raise AppError("미등록 카테고리", "category add로 먼저 등록하세요.", 3)

# budget_app/decorators.py — handle_errors 내부에서 처리하는 쪽
try:
    return function(*args, **kwargs)
except AppError as error:
    print(f"[오류] {error}\n[힌트] {error.hint}", file=sys.stderr)
    return error.code
```

AppError는 오류 내용을 담고, handle_errors는 그 내용을 출력한 뒤 종료 코드로 바꿉니다. CSV를 읽는 중 발생한 값 오류는 data_error로 문맥을 바꿔 코드 5로 전달합니다.
